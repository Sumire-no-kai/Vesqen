# M3 开发清单：USB bit-perfect 与首页性能收敛

2026-09-08。范围与完成条件以 [PRD 的 M3 章节](PRD.md) 为准；服务侧所有权遵循 [架构审查](ARCHITECTURE_REVIEW.md)。本清单同时记录代码候选与仍待执行的验收，勾选项必须按下文证据边界理解。

## 开始条件与当前结论

**M3 已有软件候选和部分真机证据，但尚未完整验收；可以并行准备 M4 开发。** M2 开放项继续由 [设备验收记录](M2_DEVICE_ACCEPTANCE.md) 跟踪。用户目前没有可用 DAC，Bluetooth 按此前要求暂缓；现有扬声器测试不能证明 USB 直出。M4 的主要任务与依赖见 [M4 开发清单](M4_IMPLEMENTATION_PLAN.md)。

Library 首页快速滑动的具体根因定位与代码修复现列为 **M3 正式交付项**，不再只是 M1/M2 遗留备注。M3 软件阶段只有在根因证据、实际修复、双机重复性能对照和功能回归全部成立后，才能把该项标记完成。

启用真实严格输出前，必须先完成下面第 2 项技术验证。M3 最终验收仍需至少两台 Android 14+ 手机及两款 USB DAC；模拟器和 Fake 测试不能替代。

2026-09-07 双机补充：Honor STF-AL00 / Android 9 已接入，用于 M2 旧系统和 M3 API 26–33 兼容路径回归；iQOO V2171A / Android 15 用于现代系统。Honor **不计作第二台 Android 14+ 设备**。实际执行结果见 M2 验收记录；目前尚未连接可验收的 USB DAC。

### 软件候选自审结论（2026-09-08）

- 修复重配、切歌和模式切换并发时的过期计划竞态：每次配置拥有 generation，旧 `getAudioOutput`、路由回调和超时任务只能保持静音，不能覆盖新状态或恢复失效的 ACTIVE。
- mixer preference 的设置、读回和清理改为使用 Media3 当前 `OutputConfig` 的实际 `AudioAttributes`，避免固定属性与真实 AudioTrack 属性不一致；失败与关闭路径保留同一属性用于精确清理。
- fail-closed 清理统一先静音并解除路由监听，再撤销 mixer preference；路由长期不可观测时在播放意图成立后等待 3 秒并明确失败，避免无限停留在 APPLYING。
- 服务命令统一回到主线程执行；进程内状态仓库和 Controller 拒绝重复或倒退 generation，避免 Session extras 与命令响应乱序覆盖新状态。
- 补齐 USB 新增设备重新判定、内部暂停恢复、输出静音门与路由监听注册异常处理，以及 Chain 对输出协调器证据来源的中英文标签。

上述自审完成时没有设备，结论仅来自源码与本地门禁。随后 iQOO 接入，执行了上表所列回归并修复 R06；本轮仍无 Honor 或 USB DAC，严格输出、真实插拔和 M3 长时资源检查未通过实物验收。

## 主要需求摘要

2026-09-08 重连补验：iQOO 英文 UI 51 项、真实音源与存储/遥测契约 15 项、无 DAC 严格模式与扬声器 2 项取得通过；另完成设置跨进程写入/读取和中文中等大字体补测。截图发现并修复英文播放器按钮省略，最终候选的英文定向 4 项、中文 1 项通过。完整批次、版本、宿主辅助和测试代理指标误报见 [设备验收记录](M2_DEVICE_ACCEPTANCE.md) 与 [案例 R08](ENGINEERING_CASEBOOK.md)。Library 复验仍未形成业务根因与实际修复证据；Honor、真实 DAC、高刷新率及用户暂缓的长时门禁继续开放。

1. 定位并修复 Library 首页快速滑动卡顿，在 Honor 与 iQOO 上完成受控的修复前后对照。
2. 检测 Android 14+ 官方 USB mixer / bit-perfect 能力，并匹配设备与曲目格式。
3. 提供普通播放与严格 USB 输出模式，服务统一管理请求、实际状态和失败原因。
4. 正确设置、核验、清除 mixer preference，处理切歌、不同格式和服务重建。
5. 严格模式约束会改写 PCM 的处理；拔出、权限/路由丢失或不支持时停止并解释，不能静默降级。
6. 播放器、Chain 与诊断显示同一证据状态；AVAILABLE / ACTIVE / VERIFIED 各有明确边界。
7. 覆盖旧 Android 回退、资源释放、故障顺序，并完成两台现代手机 × 两款 DAC 的实物矩阵。

## 按依赖顺序实施

### 1. Library 首页快速滑动定位与修复（M3 正式交付项）

- [ ] 用准备交付的 Release/profileable 构建建立双机基线：固定曲库数据、排序、屏幕刷新率、播放暂停状态、编译状态、供电与温度范围；确认没有扫描、诊断录制或其他业务干扰。
- [ ] 由新鲜 UI hierarchy 取得实际列表视口，以同一方向节奏和手势数量分别执行至少三轮；保留 `gfxinfo framestats` 原始数据，报告总帧、jank、p50/p90/p95/p99，不选取最好的一轮。
- [ ] 将慢帧对齐 iQOO Perfetto FrameTimeline / CPU 调用栈与 Honor 的有效 atrace；区分 App deadline miss、Buffer Stuffing/呈现排队、输入延迟、线程等待和真实 CPU 热点。
- [ ] 沿调用栈回到业务入口，逐项验证 `TrackRow` 组成与文字测量、Lazy 列表预取、稳定 key/content type、封面请求和重组范围。每次只改变一个变量；没有证据支持的候选不作为修复提交。
- [ ] 对确认根因实施最小代码修复，不通过关闭封面、索引、点击、拖动、无障碍或减少真实曲库数据换取帧率。
- [ ] 在 Honor 与 iQOO 的同一最终 APK 上，各完成至少三轮修复前后配对测试；三轮中位 jank 和 p95 都应改善且超过自然波动，最坏轮次不得出现未解释的明显回退，FrameTimeline/调用栈应显示已确认热点相应收敛。
- [ ] 重跑曲库点播、刷新保持视口、A–Z 索引、收藏/歌单拖动、封面与无障碍回归；把根因、改动、原始结果、限制和仍开放风险补入 [中文工程案例 P01](ENGINEERING_CASEBOOK.md)。

完成判定：必须同时具备可复现基线、慢帧与业务调用路径的根因证据、实际代码修复、双机重复改善和功能回归；只有一次更好的数字、强制 AOT、主观感觉或仅找到热点都不算完成。

### 2. 核实公开 API 与现有播放器的接入条件

- [ ] 检查项目当前 Media3 1.11.0 的 AudioSink/AudioTrack 创建路径，确认 mixer preference 与实际播放使用的设备、AudioAttributes、PCM 格式如何对应。
- [ ] 验证采样率、声道布局、PCM encoding 的能力匹配、设置、读取与清除时序，以及何时需要停止或重建输出。
- [ ] 明确系统能力报告、应用成功请求、实际输出状态各自能证明什么；无法获得的证据保留 unavailable 原因。
- [ ] 形成可测试的接入决定后再启用严格输出；保持当前 Media3 内核，不预先引入 native 引擎或自定义 USB 驱动。

### 3. 输出决策与唯一状态来源

- [ ] 实现纯逻辑 `UsbOutputStrategyResolver` / `UsbOutputDecision`，输入包含 API、USB Host、数字音频设备、格式、路由、权限和用户模式。
- [ ] 服务持有用户请求、平台设置结果及当前声明；`PlaybackSnapshot` 与 `PlaybackTelemetry` 读取同一份状态。
- [ ] 区分普通系统输出、能力可用、请求处理中、已生效和失败；过期事件不得恢复已经失效的 ACTIVE。
- [ ] 为版本、设备、格式、权限及事件顺序建立组合测试。

### 4. 官方 API 34+ 输出实现

- [ ] 隔离 `OfficialMixerBitPerfectAdapter`，查询 `getSupportedMixerAttributes()` 并匹配 bit-perfect 属性。
- [ ] 执行设置、验证和清理；将返回失败、异常与能力缺失映射为明确结果。
- [ ] API 26–33 使用普通系统路由，确保不加载或调用 API 34 专属实现。
- [ ] 将实现接入服务和现有 Media3 输出生命周期，覆盖切歌、格式变化、停止及服务重建。

### 5. 严格模式与失败处理

- [ ] 严格模式禁用应用软件音量、EQ、ReplayGain、响度处理、交叉淡化及其他会改变 PCM 的处理；检查变速等处理路径。
- [ ] 设备拔出、路由丢失、权限丢失、不支持格式或处理约束失效时停止严格输出并撤销 ACTIVE。
- [ ] 清理旧 preference 和输出资源；重复事件、快速插拔及旧异步回调不能留下失效状态。
- [ ] 普通兼容输出必须由用户明确选择，不能在失败后悄悄继续并保持严格模式声明。

### 6. 界面与 Audio Proof

- [ ] 增加模式选择、能力/失败原因、设备与格式信息，以及必要的重试或兼容模式入口。
- [ ] 解释严格模式下 DAC 音量与手机音量按键的实际行为，按实测呈现。
- [ ] 统一播放器、Chain 和诊断导出的输出声明，保留 confidence、来源、时间及不可用原因。
- [ ] AVAILABLE、ACTIVE、VERIFIED 明确区分；没有外部验证记录的组合绝不显示 VERIFIED。
- [ ] 校验诊断隐私、中文/英文、窄屏、大字体及页面进出动画。

### 7. 验证与交付门禁

- [ ] 纯逻辑、平台适配器 Fake、服务事件顺序及资源释放回归通过。
- [ ] Library 首页快滑满足第 1 节的根因、修复、双机配对性能和功能回归门禁。
- [ ] 完成本地 unit/lint/Debug/Release 与相关 instrumentation 验证；分别记录构建和执行结果。
- [ ] 实机完成至少两台 Android 14+ 手机 × 两款 DAC 的能力、格式、插拔和失败矩阵；另验证旧 Android 降级路径。
- [ ] 验证严格模式长期播放、切歌、后台、焦点变化、服务恢复及退出后的资源释放。
- [ ] 为精确 APK/ROM/DAC/格式保留证据；所有失败路径无错误 ACTIVE，未外验组合无 VERIFIED。

M4 的外部验证体系、M6 条件性内核替换、M7 实验 USB 路线不扩大为本次 M3 实现范围。

M4 适配补充待办：最终 1.5× 英文会话面板的进度标签仍有省略，读数和操作正常。后续调整信息行标签/读数布局时，应保留完整语义与读数，复查中英文和更窄窗口；本轮按钮修复不覆盖整个面板。
